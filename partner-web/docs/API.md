# Модель данных и API — WEB DEMO 0.1.0

Этот документ разделяет существующий локальный репозиторий браузера и предлагаемый серверный контракт. **HTTP API, настоящий вход и интеграции не реализованы.** `openapi.yaml` служит проектом для следующего этапа. Ни один маршрут из раздела сервера не следует считать работающим.

## Локальное демо

Приложение состоит из статических ES-модулей. Данные и изменения сохраняются в хранилище браузера. Демонстрационный выбор пользователя передаёт контекст роли в репозиторий; он проверяет разрешения на чтение и запись независимо от видимости элементов интерфейса. Проверки по прямым ID, фильтры организации и станций нужны для тестирования будущих правил. Они не защищают данные от владельца браузера.

Роли: суперадминистратор QUBAT; владелец сети; сотрудник партнёра; бухгалтер; наблюдатель. Сотруднику по умолчанию недоступна общая финансовая аналитика. Бухгалтеру недоступно управление зарядкой. Наблюдатель ничего не изменяет. Назначения станций и отдельные разрешения на экспорт, тарифы, доступы, скидки и бесплатную зарядку проверяются отдельно от названия роли.

### Модули выпуска

| Файл | Назначение |
| --- | --- |
| `dist/core.mjs` | `createDemoStore`, `DemoRepository`, точные десятичные функции и периоды |
| `dist/excel.mjs` | `exportWorkbook(report)` → `Uint8Array`, `reportFilename(report)`, `downloadReport(report)` — локальный `.xlsx` без зависимостей |
| `dist/views.mjs` | Реестр/карточки точек, доступы, бренды и модальные формы |
| `dist/app.mjs` | Оболочка, маршруты интерфейса, мониторинг, отчёты, финансы и локальное сохранение |
| `dist/style.css` | Адаптивное оформление и мобильная навигация |

Локальный API не является HTTP API и не обещает совместимости будущего backend. Минимальный вызов для тестов:

```js
import { createDemoStore, DemoRepository } from './dist/core.mjs';
import { exportWorkbook } from './dist/excel.mjs';

const store = createDemoStore('2026-11-01');
const repo = new DemoRepository(store, 'owner-a');
const report = repo.exportReport({
  from: '2026-10-01', to: '2026-10-31', stationId: 'st-a1'
});
const xlsxBytes = exportWorkbook(report);
```

Фабрика по умолчанию использует дату `2026-11-01`; это воспроизводимый срез демо, а не текущая телеметрия. `store.version = 2` — версия локальной схемы, не версия приложения. Деньги сохраняются JSON-строками, энергия имеет три знака; `BigInt` остаётся внутри арифметики и не записывается в JSON.

| `saveBrand(patch)` | `brands.edit` |

Фильтры локального отчёта: `from`, `to`, `orgId`/`organizationId`, `ownerId`, `groupId`, `locationId`, `stationId`, `portId`, `customerId`, `operation`, `paymentStatus`, `sessionStatus`. Фильтр станции также принимает `search`, `status`, `includeArchived`. Чужие организация, владелец, станция и порт отклоняются. Группа/локация ограничивается пересечением с назначенными точками. Даты проверяются, обратный диапазон запрещён. Выбор расходов `deductions` принимает `electricity`, `platformFee`, `acquiringFee`, `tax`, `rent`, `other`, дополнительно `partnerShare`, `reserve`, `payout`; неизвестная статья отклоняется.

Точные функции `decimal(value, places)`, `money(value)`, `energy(value)`, `add`, `sub`, `mul`, `div`, `percent` используют масштаб `10^6`, принимают десятичные строки до шести знаков и возвращают строки. Дробный `Number` отклоняется. Округление половин — от нуля, включая отрицательные суммы. `dateRange(from, to)` возвращает границы включённых дат и `endExclusive`; `bishkekDate(iso)` переводит временную метку в местную дату. Серверу нужен полноценный IANA-календарь: локальный выпуск использует актуальное для демо смещение UTC+06:00.

В локальных версиях тарифа `effectiveFrom/effectiveTo` — даты с включённым конечным днём; следующий тариф закрывает прежний предыдущим днём. Предлагаемый серверный контракт ниже использует полуинтервалы временных меток. Это намеренное различие должно учитываться адаптером миграции.

### Расчёты и ограничения локального выпуска

По умолчанию прибыль вычитает электричество, платформу, эквайринг, налог, аренду и прочие расходы. Доля партнёра, резерв и перевод партнёру выбираются отдельно. Выплата исключена по умолчанию: это движение денег, которое нельзя второй раз вычитать после учёта доли. Неизвестные оплаты, фактический счёт или фактическая аренда передаются `null`, а не нулём. Прибыль/маржа зависят от выбранных статей; `actualProfit` не вычисляется, если требуемого факта нет.

Фактический месячный счёт применяется только к полному месяцу без сужения до порта/клиента/операции/статуса сессии или оплаты. Для неполного периода остаются `partialPeriod: true`, сохранённая квитанция как метаданные и отдельный расчёт; месячный счёт не подставляется в расходы нескольких дней. Месячная выплата и задолженность для неполного периода возвращаются `null`.

В оценке целой точки аренда и прочие месячные суммы распределяются по календарным дням. Ставки аренды взвешиваются по дням; исторические даты опираются на сохранённые снимки. При сужении до порта/клиента/операции/статуса постоянные расходы неизвестны (`null`), поскольку произвольное распределение на отобранные сессии не утверждено. Исторические сессии содержат снимки цены и финансовых строк; тарифная правка их не переписывает.

Квитанция демо — метаданные `name`, `size`, `type`, а не загруженный и проверенный файл. В форме принимаются PDF/PNG/JPEG до 5 МиБ только для демонстрации выбора имени; содержимое не сохраняется и не отправляется. Предлагаемый сервер ниже имеет отдельный лимит 10 МиБ и проверку фактических байтов. Реальные вложения в браузерное демо не передаются.

Сессии выбираются по времени начала в `Asia/Bishkek`. Их платежи — по дате проводки внутри выбранного периода; платёж за границей периода может дать разницу сверки. Это сверка выбранного набора сессий, не полный банковский журнал всех проводок периода. Локальная сверка использует синтетические реестры и не подтверждает банковское поступление. Условия расчёта и выбранные статьи сохраняются в отчёте/Excel для проверки.

## Предлагаемая серверная архитектура

Клиенты WEB и Android обращаются к одному серверному слою бизнес-правил. Сервер содержит проверку сессии и 2FA, область организации/станций, точные расчёты, аудит, хранение версий, фоновые выгрузки и адаптеры официальных операторов. Только серверный адаптер хранит секреты и общается с оператором или OCPP-шлюзом. Телефон и браузер ключей станций не получают.

Рекомендуемое разделение модулей: identity/access, registry, tariffs, telemetry/sessions, payments/reconciliation, finance, exports, receipts, notifications/audit, operator adapters. Хранение: транзакционная БД с внешними ключами и ограничениями организации; закрытое объектное хранилище квитанций и экспортов; очередь задач; неизменяемый журнал событий и версий. Это архитектура следующего этапа, а не комплект установленной инфраструктуры.

Одна станция — один физический аппарат, даже если у неё два независимых GB/T DC-разъёма. Число аппаратов и портов хранится и агрегируется раздельно. Внешние ID уникальны в пространстве конкретного оператора; они не заменяют внутренний UUID и не дают права доступа.

## Авторизация каждого обращения

1. Проверить подтверждённую серверную сессию, активность пользователя и организации, срок назначения, отзыв и требуемый уровень 2FA.
2. Получить организацию ресурса из БД, а не доверять `organizationId` клиента. Применить пересечение прав организации, станций/групп и действия. Назначение одной станции не даёт права на остальные станции группы.
3. Ограничить запрос до агрегирования и пагинации. Прямой ID, вложенный ресурс, история, аудит, экспорт и вложение проходят те же проверки. Ресурс другой организации возвращает `404`, чтобы не раскрывать существование.
4. Любая запись выполняет повторную проверку внутри транзакции. Отзыв прав действует на следующий запрос; фоновые задачи и скачивание экспортов повторно проверяют доступ перед выдачей результата.
5. Суперадминистратор работает в явном разрешённом контексте организации; действия и смена контекста журналируются. Опасные финансовые и управляющие действия требуют подтверждения и свежего 2FA.

Общие финансовые суммы выдаются только с `finance.read`; обычного `station.read` недостаточно. Экспорт требует `report.export` и прав на каждый тип данных: запрещённые столбцы/листы не должны становиться обходом ограничения. Запрос с недоступной явно выбранной станцией отклоняется; молчаливое расширение фильтра до всей организации запрещено. История доступа и финансов не выдаётся наблюдателю только потому, что он видит станцию.

## Периоды, точность и версии

- Валюта всех денежных значений — `KGS`. HTTP передаёт суммы строками вида `"135.00"`; ставки — десятичными строками с согласованной точностью, энергию — отдельно, например `"12.345"`. На сервере применяются `NUMERIC/DECIMAL` либо масштабированные целые. `float` и `double` для денег не используются.
- Временные метки хранятся как UTC `date-time`; отчёты и месяцы строятся в IANA-зоне `Asia/Bishkek`. Период дат `from=2026-10-01&to=2026-10-31` означает `[2026-10-01T00:00:00+06:00, 2026-11-01T00:00:00+06:00)`. Граница конца даты включается только через следующий день, без `23:59:59`.
- Суммы округляются до тыйынов по согласованному правилу половин от нуля (`half-away-from-zero`) на границе финансовой строки; энергия и промежуточные произведения сохраняют исходную точность. Версия правила округления фиксируется в расчёте. Нельзя повторно округлять уже зафиксированную сумму при каждом чтении отчёта.
- Тариф клиента, электричество, комиссия платформы, эквайринг, налог, аренда, доля партнёра и удержания — независимые параметры. Налог не зашивается константой `4%`.
- Версии действуют в непересекающихся интервалах `[effectiveFrom, effectiveTo)`. Новая версия не меняет цену завершённой сессии. Политика смены тарифа внутри активной сессии должна быть согласована с оператором; по умолчанию цена фиксируется при старте.
- Финансовые условия фиксируются ссылкой на версию и снимком рассчитанных строк. Исправление закрытого периода создаёт отдельную корректировку с причиной, автором и временем. Оно не перезаписывает первичный документ.

Оплаченная выручка = успешные оплаты − успешные возвраты. Начислено, но не оплачено, показывается отдельно. Расчётное электричество = энергия завершённых учтённых сессий × действовавшая закупочная ставка. Фактический счёт хранится рядом с расчётным, вместе с периодом, номером, оплатой и разницей. В режиме «Фактический» отсутствующий счёт отмечается как неполный период: нулевой счёт или молчаливая подстановка расчёта недопустимы.

Прибыль = оплаченная выручка − расходы выбранного режима − начисленная доля партнёра/договорные удержания, если они входят в утверждённую модель. Маржа = прибыль / выручка × 100 только при выручке > 0. Выплата погашает обязательство перед партнёром; повторно вычитать выплату, если доля уже учтена расходом, нельзя. Движение денег и задолженность показываются отдельно. Акт сверки сравнивает сессии, поступления платёжного провайдера, возвраты и комиссии; необъяснённая разница выделяется.

## Предлагаемые маршруты

Префикс `/api/v1`. Относительные адреса в [openapi.yaml](openapi.yaml) намеренно не указывают реальную инфраструктуру.

| Маршрут | Требование |
| --- | --- |
| `POST /auth/otp/requests`, `/auth/otp/verifications`, `/auth/step-up` | Будущий подтверждённый вход, ограничение попыток, 2FA; не доступен в демо |
| `GET /me`, `GET /organizations` | Только членства текущего пользователя |
| `GET/POST /organizations/{organizationId}/stations` | Область организации, назначенные станции; запись с `station.write` |
| `GET/PATCH /organizations/{organizationId}/stations/{stationId}` | Прямой ID проверяется; оптимистическая версия при записи |
| `GET/POST .../stations/{stationId}/tariffs` | Просмотр/изменение тарифа раздельны, версия и preview |
| `GET .../stations/{stationId}/history` | Дополнительное право на историю, без утечки чужих записей |
| `GET .../sessions`, `GET .../payments`, `GET .../reports/summary` | Фильтры до агрегации, персональные поля по отдельному праву |
| `POST/GET .../exports`, `GET .../exports/{exportId}/download` | Только разрешённые строки и поля, повторная проверка перед скачиванием |
| `GET/POST .../financial-terms`, `GET .../finance/months` | Финансовая роль, версии условий, точные суммы |
| `GET/POST .../expenses`, `PATCH .../expenses/{expenseId}` | Разрешённые станции, аудит и версия |
| `POST .../receipts/uploads`, `POST .../receipts/{receiptId}/complete`, `GET .../receipts/{receiptId}/download` | Закрытое хранилище и проверка файла |
| `POST .../payouts`, `GET .../reconciliation` | Отдельное право, 2FA, идемпотентность, сверка |
| `GET/POST .../memberships`, `PATCH/DELETE .../memberships/{membershipId}` | `access.manage`, нельзя назначить права выше собственных |
| `POST .../discounts`, `POST .../free-charge-grants` | Отдельные разрешения, срок, лимиты и одобрение |
| `POST .../stations/{stationId}/commands`, `GET .../commands/{commandId}` | Только будущая разрешённая интеграция; идемпотентность и подтверждение |
| `GET .../audit`, `GET .../notifications` | Область станции и специальные права |
| `POST /integrations/{integrationId}/events` | Отдельная сервисная аутентификация, подпись, дедупликация |

Типовые ответы: `401` — нет сессии; `403` — нет разрешения; `404` — ресурс отсутствует или вне области доступа; `409` — конфликт версии/ключа идемпотентности; `422` — неверные данные; `429` — лимит запросов. Ошибка содержит безопасный код, сообщение и `requestId`, без ключей интеграций и трассировок.

## Идемпотентность, события и состояние станции

Каждая выплата, финансовая корректировка и команда имеет `Idempotency-Key`, привязанный к организации, пользователю/сервису и операции. Сервер атомарно сохраняет хеш тела и результат. Повтор с тем же ключом и телом возвращает прежний результат, с другим телом — `409`. Запрос не повторяет оплату или старт сессии. Ключи и результаты хранятся не меньше согласованного срока повторов провайдера; для денежных проводок сохраняются постоянные уникальные бизнес-ID.

Команда проходит состояния `queued`, `sent`, `accepted`, `succeeded`, `failed`, `timed_out`, `unknown`. Принятие HTTP-запроса не означает успех оборудования. После тайм-аута нельзя автоматически отправлять новый старт с новым ключом: сначала нужно получить результат/статус у оператора. UI показывает источник, статус, время и причину результата.

Входящее событие уникально по `(integrationId, sourceEventId)`. Хранятся `occurredAt`, `receivedAt`, исходный ID сессии/платежа, последовательность/версия оператора и обезличенный исходный payload. Повтор не создаёт новую сессию или проводку. Позднее событие не заменяет более свежую телеметрию старым состоянием. Пропуски и поздние завершения попадают в сверку и, при необходимости, явную корректировку периода. Условия завершения и политика допуска опоздания согласуются с официальным источником.

Наличие связи определяется по времени последнего подтверждённого сигнала с настраиваемым порогом. Старые показания не окрашиваются как свежая доступность. Мгновенная мощность, энергия сессии и показания внешнего счётчика хранятся отдельно.

## Квитанции и экспорт

Загрузка квитанции в настоящем backend проходит три стадии: создание метаданных и ограниченного upload URL; загрузка; завершение с проверкой размера, MIME, сигнатуры и антивирусного статуса. Предлагаемый лимит — 10 МиБ, типы PDF/JPEG/PNG. Расширение и заголовок клиента не считаются проверкой. SVG/HTML, исполняемые и архивные файлы не принимаются; файлы в карантине недоступны для просмотра. Имена файлов нормализуются, путь и имя объекта назначает сервер. Хеш, владелец, период, автор и связь с расходом сохраняются в БД.

Объекты закрыты; короткоживущий signed URL выдаётся после проверки `receipt.read` и области организации/станции. URL привязан к объекту и конкретному действию, не открывает список хранилища и не даёт права перезаписи. Для чувствительных документов предпочтительна авторизованная прокси-выдача. В журнал не пишутся полные URL с подписями. Отзыв доступа применяется до выпуска ссылки; срок жизни минимален. В демо нет серверного хранилища и проверки файлов.

Excel содержит пять листов: «Сводка», «Сессии», «По станциям», «Платежи», «Расходы». Включаются период, зона, применённые фильтры, валюта и время построения. Числа имеют числовой формат Excel; пользовательский текст записывается как текст, без формул и внешних ссылок. Выгрузка не содержит лишних персональных данных. Сервер строит её по согласованному снимку/границе данных, повторно проверяет права до выдачи, задаёт срок хранения и удаляет по политике хранения. ID фоновой задачи или знание ссылки не даёт доступ к чужой выгрузке.

## Вопросы к официальному оператору

Нужно получить письменное разрешение, документацию и sandbox. Не предполагается наличие открытого API у Charge24, Spark, Pay24, EEJANN. Уточнить:

1. Какие read-only методы статусов, станций, портов, сессий, тарифов и платежей доступны; как выдаются учётные данные и область владельца?
2. Какие внешние ID стабильны; как заданы аппарат и порт; поддерживаются ли несколько разъёмов и разделение мощности?
3. Какова точность кВт·ч, денег и времени; какая зона исходных данных; где фиксируется тариф и как учитываются возвраты/комиссии?
4. Есть ли webhooks, подписи, номера последовательности, повторная доставка, лимиты, cursor-пагинация и историческая выгрузка? Как исправляются поздние и ошибочные записи?
5. Как сверять с эталонным отчётом; доступны ли тестовые платежи, возвраты, неоплаченные и отменённые сессии?
6. Какие команды действительно поддерживаются моделью станции; каковы подтверждение, timeout, idempotency и процедура испытания отдельной станции?
7. Кто владеет данными, каковы хранение, резервное копирование, отзыв доступа, SLA и процедура ротации ключей?

До согласования ответов подключения, реальные платежи и команды оборудования остаются выключены.
